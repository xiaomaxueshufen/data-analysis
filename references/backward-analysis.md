# 倒推式分析设计协议

## 目的

不要从“手头有什么字段”直接跳到“能画什么图”。先从用户需要做的业务决定倒推结论所需的比较、证据和数据条件；字段不足时，明确降级答案，而不是用行业常识填空。

## 倒推链

按下面顺序逐层回答：

```text
业务决策
  → 需要相信什么结论
  → 结论需要哪些比较
  → 比较需要什么基线/对照
  → 基线需要哪些字段和粒度
  → 字段是否存在且质量合格
  → 选择方法与图表
  → 产出证据合同
```

每一层都必须写出“当前问题、所需字段、当前状态、缺失时的降级答案、可达到的结论层级”。

## 模型提示词

```text
你是面向业务决策的数据分析师。请不要先选择图表，也不要因为字段名称像某个指标就默认口径成立。

先把用户问题改写成一个明确的决策：谁要在什么时间点，根据什么结果做什么选择？
然后按以下顺序倒推：
1. 该决策真正需要相信的一到三个结论是什么？把事实、比较、解释和行动含义分开。
2. 每个结论需要怎样的比较：时间前后、组间、漏斗阶段、结构/组内、处理/对照，还是目标/承诺？
3. 每个比较的基线或对照是什么？说明为什么可比，以及哪些日期、群体或记录必须排除。
4. 基线需要哪些字段、实体、分母、时间粒度和维度？区分原始字段、可重算字段和业务事件字段。
5. 对照数据是否真的存在？检查缺失、延迟、字段置空、粒度不一致、重复实体和分组不可加总。
6. 只有在字段与质量门禁通过后，才选择分析方法、计算算子和图表。图表必须服务于一个具体问题。
7. 为每个结论建立证据合同：statement、level、evidence_ids、formula、baseline、limitations、follow_up_data。

输出 JSON，不写无法被用户数据支持的原因：
{
  "decision": "",
  "backward_steps": [
    {
      "step": 1,
      "question": "",
      "needed_fields": [],
      "available": true,
      "quality_status": "confirmed|inferred|missing|blocked",
      "fallback": "",
      "max_claim_level": "L0|L1|L2|L3|L4"
    }
  ],
  "selected_methods": [],
  "selected_charts": [],
  "contract": {
    "metric": {},
    "grain": "",
    "baseline_or_control": "",
    "exclusions": [],
    "assumptions": []
  },
  "missing_data": [],
  "stop_conditions": []
}
```

## 结论层级控制

- 只有当前值和原始记录：最多 L0；
- 有可比基线或对照：可以到 L1；
- 有分解对账、时间顺序和独立字段：可提出 L2 候选；
- 有明确可行动的决策规则、责任对象和验收指标：才考虑 L3/L4；
- 缺少关键分母、处理时间、对照组或事件日志时，必须停在较低层级，并列出补数方案。

## 与方法路由的关系

倒推协议先于方法选择。异动、漏斗、贡献度、AB、因果和分层可以组合，但每个组合都必须共享同一个决策、指标口径和排除区。多个方法只是在回答不同的证据问题，不是把多个弱证据叠加成确定因果。
